# 引導式探索模式（Guided Exploration Mode）設計

> 文件版本：2026-04-23  
> 對應架構：`backend/app/services/llm_service.py`、`frontend/src/pages/CourseSearchPage.tsx`

---

## 一、背景與設計動機

### 1.1 現有架構的限制

目前系統採用**全自主 ReAct 架構**（max_rounds=4）：LLM 一旦收到問題，就自動執行工具、自主決策所有查詢方向，直到生成最終回覆。這個模式對「有明確目標的使用者」效果很好，但針對**高中生探索情境**，存在兩個核心風險：

**風險一：語意漂移（Semantic Drift）**

高中生往往不知道自己想問什麼，第一句話很模糊。LLM 一旦猜測意圖出錯，後續每一輪都在錯誤方向上累積，結果越偏越遠。

```
使用者：「我對 AI 有興趣」
LLM 猜：應用類 → 呼叫 search_courses("AI 應用")
         → 找到企業資料分析課程
         → 繼續延伸找管理類課程
         → 使用者其實想學機器學習理論 ❌
```

**風險二：過早承諾（Over-commit）**

LLM 選了第一個工具後，就「一路走到底」，即使中途發現結果不確定，也不會退回來詢問使用者。因為目前的架構沒有任何「暫停 → 詢問」的機制。

### 1.2 引導模式的本質

引導模式不是「速度較慢的模式」，而是**控制權分配的不同**：

| | 自主模式（Autonomous） | 引導探索模式（Guided） |
|---|---|---|
| 控制權 | LLM 全程決策 | LLM 在不確定點把決策交回使用者 |
| max_rounds | 4 | 2 |
| 使用者參與 | 無（只看結果） | 在關鍵決策點選擇方向 |
| 適合情境 | 明確問題、fact lookup | 模糊探索、高中生初探 |
| 語意漂移風險 | 高 | 低 |

## 二、高中生查詢模式分析

高中生在探索大學課程時，帶有三個典型的知識限制：
- **不懂課程體系**：不知道什麼是「必修/選修」、「學分學程」、「跨院課程」
- **知識來源片面**：多從新聞、YouTube、朋友聽說，對科系/課程理解停留在表面
- **目標模糊**：知道自己「喜歡」某個領域，但不知道這映射到哪些具體課程或科系

這些特性造成以下 7 種典型查詢模式，每種需要不同的引導策略：

---

### 模式一：廣泛領域探索

**典型問法**
> 「我對 AI 有興趣」  
> 「我喜歡電腦相關的東西」  
> 「我對天氣和氣候很感興趣」  
> 「我喜歡生物，想和醫療結合」  
> 「我對環境保護有興趣」

**問題根源**

這類詞語在高中生眼中是具體感受，但對大學課程來說仍然過於廣泛。「AI」涵蓋 NLP/CV/ML/應用，「天氣」可能是大氣科學系、地球科學系或環境工程系，「生物+醫療」可能是生醫工程、物理治療或生命科學。LLM 隨機猜一個方向，很高機率猜錯。

**引導策略**：Pre-flight 觸發，提供 3-4 個具體方向供選擇，**每個選項附上白話說明**，幫助高中生理解每個方向是什麼。

```
（AI 的例子）
你比較想探索 AI 的哪個方向？
[🧠 機器學習理論]  讓電腦從資料中學習
[💬 自然語言處理]  讓電腦理解語言，ChatGPT 背後的技術
[👁️ 電腦視覺]     讓電腦「看懂」圖片和影片
[⚡ AI 應用開發]  用現有 AI 工具做出產品

（天氣/氣候的例子）
你對「天氣氣候」的哪個面向比較感興趣？
[🌧️ 氣象預報原理]  颱風、降雨的物理機制
[🌡️ 氣候變遷科學]  溫室氣體、全球暖化
[🛰️ 遙測與資料分析] 衛星資料處理
[🌍 環境影響評估]  氣候政策、永續發展

（生物+醫療的例子）
「生物醫療」的方向有很多，你比較想往哪裡走？
[🏥 生醫工程]     設計醫療器材、義肢、影像系統
[🧬 生命科學]     基因、細胞、分子生物
[🏃 物理治療/復健] 人體動作與康復
[💊 藥學/新藥開發] 藥物設計與臨床
```

---

### 模式二：職涯導向查詢

**典型問法**
> 「我想當工程師要讀什麼系？」  
> 「我想從事醫療相關工作，要學什麼？」  
> 「我想成為老師，中央大學有相關科系嗎？」  
> 「想做環境保護或永續發展的工作要讀什麼？」  
> 「我喜歡文學，可以靠寫作維生嗎？」

**問題根源**

「工程師」對高中生是個模糊概念（軟體/硬體/機械/環境工程全算），「醫療工作」分為生醫工程、物理治療、生命科學等截然不同的路線，「文學創作」在不同系所的定義也大相逕庭。目標不確定，課程推薦就沒有意義。

**引導策略**：Pre-flight 觸發，先問哪個方向，再對應到系所。

```
（工程師的例子）
「工程師」的方向很多，你比較想做哪一種？

[💻 軟體工程師]  寫網頁、App、後端系統
[🤖 AI 工程師]   訓練模型、做 AI 產品
[🔌 電子/嵌入式] 硬體、韌體、電路設計
[🌿 環境工程師]  水資源、空氣污染防治、永續規劃

（醫療工作的例子）
「醫療相關工作」涵蓋很多不同方向：

[🏥 生醫工程]     設計醫療器材、手術機器人
[🏃 物理治療/復健] 協助病患恢復身體功能
[🧬 生命科學研究]  研究基因、細胞和疾病機制
[📋 公共衛生/政策] 推動健康政策與疾病預防

（文學/寫作的例子）
「文學和寫作」在大學有很多不同方向：

[📖 中文文學創作]  古典文學、現代散文與小說
[📰 媒體/新聞寫作] 採訪報導、數位媒體製作
[🌐 外文/翻譯]     英語文學、文化研究、口筆譯
[📚 教育/中文教師] 語文教學、教材設計
```

### 模式三：技能目標查詢

**典型問法**
> 「我想學程式」  
> 「我想學設計」  
> 「我想學語言，有沒有相關課程？」  
> 「我想學統計」  
> 「我想學音樂相關的東西」

**問題根源**

技能目標通常是正確的起點，但太廣泛。「學程式」的目的不同（做網頁 vs 做 AI vs 做遊戲），「學語言」也可能是學客語、英語、程式語言或語言學理論，對應的課程和科系完全不同。

**引導策略**：Pre-flight 觸發，問學習目的，選項對應到具體技術或學科方向。

```
（學程式的例子）
學程式可以有很多不同方向，你比較感興趣的是？

[🌐 網頁/App 開發]   做給人用的介面和系統
[📊 資料分析/AI]    分析數據、訓練 AI 模型
[🎮 遊戲開發]       做 2D/3D 遊戲、遊戲引擎
[🔒 資安/系統程式]  作業系統、網路、資安攻防
[📱 先學基礎就好]   Python/C++ 入門，還沒決定方向

（學語言的例子）
「學語言」有很多不同方向：

[🗣️ 客語/台語/方言]   本土語言文化與保存
[🌐 英語文學與翻譯]   英文閱讀、口筆譯訓練
[📖 語言學理論]       研究語音、語法、語意結構
[💻 程式語言]         Python、Java 等電腦語言

（學音樂的例子）
「音樂」也有不同面向：

[🎵 音樂理論/作曲]   和聲學、作曲技法
[🎻 演奏/表演]       樂器訓練、音樂會實踐
[🎚️ 音效/音樂科技]  數位音樂製作、聲音工程
[🎓 音樂教育]        學校音樂教師培訓
```

### 模式四：系所比較

**典型問法**
> 「資工和資管有什麼差別？」  
> 「中文系和外文系哪個比較好？」  
> 「大氣科學系和地球科學系差在哪裡？」  
> 「客家文化學院和中文系有什麼不同？」  
> 「讀生醫工程還是生命科學比較好？」

**問題根源**

「比較好」沒有客觀答案，取決於使用者的興趣偏向（偏理論/偏實作/偏文化）。LLM 直接回答比較容易給出「都很好」的無意義回覆，且高中生對各系所實際學什麼根本不清楚。

**引導策略**：先問使用者的興趣偏向，再根據選擇推薦適合的系所，並搭配淺顯說明。

```
（資工 vs 資管的例子）
「資工」和「資管」各有不同偏重，先了解你比較喜歡哪種感覺？

[🔧 喜歡技術/系統，喜歡寫程式] → 資工方向
[📈 喜歡商業/管理，想結合 IT]  → 資管方向
[🎨 喜歡介面設計、使用者體驗]  → 多媒體/設計系方向
[🤷 我都可以，幫我分析兩者課程差異]

（中文系 vs 外文系的例子）
「中文系」和「外文系」各有側重，先了解你對什麼更有感？

[📜 喜歡古典詩詞、文言文、中國歷史] → 中文系方向
[🌍 喜歡英文影集、旅行、跨文化]     → 外文系方向
[🗣️ 喜歡語言本身：語法、翻譯、語音] → 兩者都有語言學，偏重不同
[✍️ 喜歡寫作和創作，不限語種]        → 兩者都有，方向不同

（大氣科學 vs 地球科學的例子）
「大氣科學」和「地球科學」聽起來很像，其實差距很大：

[🌧️ 對颱風、降雨、氣象預報更感興趣] → 大氣科學系
[🌋 對地震、板塊、地質礦物更感興趣]  → 地球科學系
[🌌 對天文、太空、行星更感興趣]       → 天文所或物理系
[🌍 對環境整體、永續、海洋更感興趣]  → 環境工程或海科所
```

### 模式五：同名課程查詢

**典型問法**
> 「演算法在學什麼？」  
> 「統計學是什麼課？」  
> 「普通化學在學什麼？」  
> 「普通生物學有什麼用？」  
> 「社會學在學什麼？」

**問題根源**

「統計學」、「普通化學」、「普通生物學」這類課程在幾乎每個學院都有版本，但各科系的側重點、深度和應用情境大相逕庭（理學院 vs 管理學院的統計學截然不同）。LLM 隨機選一門代表所有，可能給出不準確的介紹。

**引導策略**：工具查詢後偵測到同名多課，觸發選擇（觸發條件五）。

```
（演算法的例子）
「演算法」這門課在多個科系都有開，內容側重略有不同：

[📐 資訊工程學系 演算法]  偏理論證明與複雜度分析
[💼 資訊管理學系 演算法]  偏應用與資料處理
[🔢 應用數學系 演算法]    偏數學推導
[🔍 了解所有課的共通點]

（統計學的例子）
「統計學」有很多版本，各科系關注的問題不同：

[📊 數學系 統計學]    嚴格的機率論與推論統計
[🧬 生命科學統計]    生物實驗設計與資料分析
[📈 管理學院統計]    商業調查、市場分析應用
[🌧️ 大氣/地科統計]  氣象資料處理、時間序列
[🔍 了解所有版本的共同核心]

（普通化學的例子）
「普通化學」根據科系而有不同深度：

[🧪 化學系 普通化學]   全面的化學原理，含計算
[🌱 生命科學普化]     以生物應用為核心
[⚗️ 化工系 普通化學]  著重工業製程與反應
[🔍 了解共通知識點]
```

### 模式六：技術名稱查詢（通常不需引導）

**典型問法**
> 「我想學 Python」  
> 「有沒有教 React 的課？」  
> 「哪裡有 SQL 課程？」

**問題根源**：幾乎沒有。技術名稱夠具體，可以直接用 `tech` 參數查詢。

**引導策略**：不觸發，直接執行 `search_courses(query="...", tech="Python")`。

### 模式七：學習路徑規劃

**典型問法**
> 「想做 AI 工程師要修哪些課？」  
> 「我想從事氣象研究，大學應該修哪些課？」  
> 「我對客家文化有興趣，中央大學有哪些相關系所和課程？」  
> 「我想念醫學院研究所，大學要先準備什麼？」  
> 「大學四年的課程規劃是什麼？」

**問題根源**

學習路徑規劃是多步驟問題，需要先確定目標（哪個領域？哪個科系？學士 or 碩士方向？），才能給出有意義的路徑。高中生對大學「必修/選修」體制完全不熟悉，直接列出課程清單也看不懂。

**引導策略**：Pre-flight 觸發，先問目標方向，再針對性規劃，並在回覆中解釋「必修」和「選修」的意義。

```
（AI 工程師路徑）
幫你規劃學習路徑前，先了解你的目標：

[🎓 想在大學好好打理論基礎]  → 推薦必修與核心選修
[🚀 想盡快做出 AI 產品]       → 實作課程路線
[🔬 想念研究所做 AI 研究]      → 學術路線規劃
[🏢 想進 AI 公司就業]          → 技能樹 + 實習方向

（氣象研究路徑）
氣象/大氣科學的學習方向：

[🌧️ 大氣科學系主修]    完整的天氣預報、數值模擬訓練
[📡 遙測與衛星資料]    跨領域結合資訊與大氣
[🌡️ 氣候變遷研究]     長期氣候分析與政策研究

（客家文化路徑）
探索客家文化有幾個角度：

[🗣️ 語言與文學]     客語學習、客家文學作品
[🎨 文化與藝術]     傳統工藝、客家音樂與祭典
[📖 歷史與社會]     族群關係、客家移民史
[🌐 全部一起了解]   客家學院的整體課程規劃
```

## 三、Decision 觸發條件設計

引導模式共有 **5 個觸發條件**，分為兩個階段觸發：

- **Pre-flight 階段**（工具執行前）：條件一
- **工具結果檢查階段**（執行後）：條件二～五

觸發時發出新的 SSE 事件 `ask_user`，之後發送 `done`（`needs_input=True`），前端顯示選項。

---

### 觸發條件一：查詢過於模糊（Pre-flight）

**觸發時機**：Stage 1 第一輪，LLM 分析 query 時

**判斷邏輯**：
- Query 長度 ≤ 5 字，**且** 不含明確課程名稱、技術名稱、系所名稱
- **或** query 中出現廣泛關鍵詞（以下任一）：
  - 領域詞：「AI」「人工智慧」「電腦」「資訊」「科技」「資料」
  - 技能詞：「程式」「設計」「工程」「分析」
  - 模糊情感詞：「有趣」「好玩」「推薦」「熱門」「有前途」「好找工作」

**詢問策略**：依 query 關鍵詞對應到最相關的選項集（見第二節各模式的選項設計）

**範例**：
```
query = "我對 AI 有興趣"
→ 偵測到廣泛詞 "AI"
→ 觸發：提供 AI 子方向選項
```

---

### 觸發條件二：語意搜尋信心低

**觸發時機**：`search_courses` 工具執行完畢（tool_done 事件後）

**判斷邏輯**：
- 所有回傳結果的 ChromaDB distance 均 > 0.7（scale 0=完全相同，1=完全不相關）
- **或** 回傳結果數量 < 3 筆

**詢問策略**：提供 query refinement，引導使用者換個說法

```
我沒有找到很相關的課程，可能是關鍵詞不夠精確。
你是不是想找這些方向？

[搜尋「機器學習」相關課程]
[搜尋「資料分析」相關課程]
[換個說法重新描述]
```

**補充**：工具回傳時需附帶 `low_confidence: bool` 旗標（目前已有 `scores` 欄位，可從此計算）

---

### 觸發條件三：多叢集結果（語意分裂）

**觸發時機**：`search_courses` 執行完畢，結果 ≥ 8 筆

**判斷邏輯**：
- 回傳課程的 `domain_tags` 集合涵蓋 3+ 個彼此不相干的領域
- 不相干定義：不在同一個 college 且 domain_tags 無交集

**詢問策略**：依 domain_tags 歸納出 2-4 個分類，讓使用者選擇

```
找到很多課程，分布在不同領域：

[🧠 機器學習/深度學習]  8 門課
[📊 資料科學/統計]      5 門課
[💬 自然語言處理]       4 門課
[📦 全部一起看]
```

---

### 觸發條件四：結果過多

**觸發時機**：`_collect_course_pool()` 執行完畢後

**判斷邏輯**：`course_pool` 大小 > 20 筆

**詢問策略**：依系所（dept）或學院（college）分組，讓使用者選擇範圍

```

[工學院]         8 門
[理學院]         5 門
[其他學院]       3 門
[全部顯示]
```

### 觸發條件五：同名課程模糊

**觸發時機**：`get_course_knowledge_map` 或 `find_similar_courses` 回傳結果時

**判斷邏輯**：找到 ≥ 3 個科系都有相同名稱的課程

**詢問策略**：列出所有科系版本 + 「了解共通點」選項

**補充**：工具需回傳 `ambiguous: bool` 和 `candidates: list[{dept, course_code}]` 欄位

### 4.1 新增 SSE 事件：`ask_user`

在現有 7 種 SSE 事件基礎上，新增一種：

```json
    },
    {
      "id": "nlp",
      "label": "自然語言處理（NLP）",
      "description": "ChatGPT 背後的技術、文字分析",

  "decisions_used": 1,
  "max_decisions": 2
}
```

**欄位說明**：

| 欄位 | 說明 |
|------|------|
| `trigger` | 觸發原因，前端可據此決定 UI 樣式 |
| `options[].query_hint` | 使用者選擇後，前端構建新 query 的關鍵詞提示 |
| `options[].description` | 白話說明，幫助高中生理解選項含義 |
| `allow_text_input` | 是否顯示「自行輸入」欄位 |
| `decisions_used` | 本次已用決策次數（前端可顯示進度） |
| `max_decisions` | 最大決策次數，達到後不再詢問 |

發出 `ask_user` 後，緊接著發出：
```json
{
  "type": "done",
  "needs_input": true,
  "paused_context": {
    "original_query": "我對 AI 有興趣",
    "trigger": "vague_query",
    "decisions_used": 1
  }
}
```

### 4.2 對話延續機制（純 SSE 可行方案）

由於目前是**單向 SSE**（不支援 WebSocket 雙向通訊），引導互動透過以下流程實現：

```
使用者輸入問題
      ↓
後端 stream_with_tools() 執行
      ↓
偵測到觸發條件
      ↓
emit ask_user 事件
emit done (needs_input=True)
      ↓              ← SSE 結束
前端顯示選項按鈕
      ↓
使用者點選選項
      ↓
前端構建新 query（原始問題 + 選擇）
發送新的 POST /chat/stream 請求
（帶同一個 session_id）
      ↓
後端讀取對話歷史，看到使用者的選擇
執行工具，進入 Stage 2
      ↓
emit token / done 正常回覆
```

**新 query 構建規則**（前端實作）：

```typescript
function buildContinuationQuery(
  originalQuery: string,
  selectedOption: AskUserOption
): string {
  if (selectedOption.id === "all" || !selectedOption.query_hint) {
    return originalQuery;
  }
  return `${originalQuery}，我想了解${selectedOption.label}方向的課程`;
}

// 範例：
// 原始：「我對 AI 有興趣」
// 選擇：「機器學習 / 深度學習」
// 新 query：「我對 AI 有興趣，我想了解機器學習 / 深度學習方向的課程」
```

## 七、與兩階段設計的整合

引導模式和兩階段設計（Stage 1 ReAct + Stage 2 回覆）是**相互獨立但互補**的設計。

```
引導探索模式的流程位置：

[使用者 query]
      ↓
[Pre-flight 觸發？]  ← 引導模式獨有
  ↓ 是 → ask_user → 等待選擇 → 新 query
  ↓ 否
[Stage 1: ReAct 工具執行]（max_rounds=2）
      ↓
[結果品質觸發？]  ← 引導模式獨有
  ↓ 是 → ask_user → 等待選擇 → 新 query → 重回 Stage 1
  ↓ 否
[Stage 2: 最終回覆生成]
（以 <course> 標籤輸出課程名稱）
      ↓
[前端解析 <course> → 課程卡片]
      ↓
DONE
```

**關鍵整合點**：
- `ask_user` 事件在 Stage 1 結束前或 pre-flight 階段發出，Stage 2 不觸發
- 使用者選擇後，前端發送的新 query 走完整的 Stage 1 + Stage 2 流程
- `decisions_used` 計數跨越多輪 query（存在 session 中），達到 `max_decisions=2` 後不再詢問

## 八、max_decisions 設計與降級策略

### 8.1 為什麼限制為 2 次？

- 詢問 1 次：縮小方向（哪個領域？哪個目標？）
- 詢問 2 次：進一步精確（哪個科系？哪個時間段？）
- 詢問 3 次以上：使用者體驗變差，感覺「這個系統在逼問我」

### 8.2 達到 max_decisions 後的降級策略

當 `decisions_used >= max_decisions`，即使觸發了條件二～五，也**不再發出 ask_user**，改為：

1. 直接進入 Stage 2 回覆生成
2. Stage 2 system prompt 加一條：「若結果有多種可能，請在回覆末尾說明『你也可以繼續告訴我更具體的需求，我可以給你更精確的推薦』」

### 8.3 三輪策略示意

```
第一輪問題：「我想從事醫療相關工作」
  → decisions_used=0 → 觸發條件一（職涯導向廣泛詞）→ 詢問「哪個方向？」
  
使用者選擇：「生醫工程」（decisions_used=1）
第二輪 query：「我想從事醫療相關工作，我想了解生醫工程方向的課程」
  → search_courses("生醫工程 醫療器材") → 14 筆
  → domain_tags 涵蓋：工程、生命科學、電子醫療 3 個領域 → 觸發條件三
  → decisions_used=1 < 2 → 詢問「哪個子方向？」
  
使用者選擇：「醫療影像與訊號處理」（decisions_used=2）
第三輪 query：「生醫工程，我想了解醫療影像和訊號處理方向的課程」
  → search_courses("醫療影像 訊號處理 超音波") → 8 筆
  → 即使 pool > 20，decisions_used=2 = max_decisions → 不再詢問
  → 直接進 Stage 2

[Stage 2 回覆]
「生醫工程在醫療影像方向有幾門很有特色的課程...

（如果你想進一步了解特定課程或科系，歡迎繼續告訴我）」
```

## 九、設計決策摘要

| 決策 | 選擇 | 理由 |
|------|------|------|
| 互動機制 | 純 SSE + 新請求 | 無需 WebSocket，相容現有架構 |
| 最大詢問次數 | 2 次 | 平衡引導效果與使用者耐心 |
| 預設模式 | 引導探索 | 高中生初探情境為主 |
| 觸發順序 | Pre-flight → 工具後 | Pre-flight 可最早攔截，避免不必要的工具呼叫 |
| 選項生成 | LLM 動態生成 vs 預設模板 | 建議先用**預設模板**（依觸發類型），再考慮 LLM 動態生成 |
| Fallback | 達到 max_decisions → Stage 2 | 確保任何情況都能給出回答，不卡死 |

## 十、待討論與後續工作

1. **選項生成是否需要 LLM？** 目前設計是 LLM 在判斷觸發條件的同時生成選項；也可以用預設模板（trigger=vague_query 時固定顯示某幾個選項）。模板方法快但彈性低，LLM 生成慢但更貼合情境。

2. **decisions_used 的作用域**：應該以 session 為單位計算（同一對話的多輪問答共享計數），還是以單輪為單位？建議以 session 為單位，避免使用者在同一對話中被反覆詢問。

3. **前端 ask_user 卡片的動畫**：選項按鈕點擊後的 transition，以及新請求發送時的 loading 狀態設計，需要和 UI 設計討論。

4. **AB 測試設計**：未來可以進行引導模式 vs 自主模式的使用者滿意度比較，作為論文的實驗設計。

5. **自主模式中的被動引導**：即使在自主模式下，觸發條件五（同名課程）仍可以考慮在回覆文字中加一句「如果你想了解特定科系的演算法課，可以告訴我」，作為輕量級引導。
