# NCU Course Advisor

國立中央大學「選課助理暨大專研究計畫」AI 平台。以知識圖譜、多信號檢索與多代理人 RAG，
服務高中生的科系探索與大學生的選課規劃。

> 想看更完整的系統設計與技術細節，請見 **[docs/final-report.md](docs/final-report.md)**（架構、
> 資料規模、各功能實作細節、資料庫 Schema）；部署與環境設定請見
> **[docs/deployment.md](docs/deployment.md)**。

## 動機

本專案要解決兩個交織的問題：**選課資訊零散**，以及**高中生無法具體理解「科系在做什麼研究」**。

### 問題一：選課資訊零散

大學選課存在嚴重的**資訊零散**問題。以中央大學為例，課程資訊分散於課務系統、教務處應修
科目表、課務資訊網學分學程、Collego 科系介紹等多個來源；修課資格（先修、限修、開放對象與
排除條件）以自然語言散落在各課程說明裡。傳統關鍵字搜尋難以處理這類問題：使用者的用詞（如
「深度學習」）常與資料中的用詞（如「神經網路」）不一致；「哪些系所有教某個技術」需要跨越
「技術—課程—系所」的多跳關係；「我這個學院的學生可以修哪些課」則需要理解複雜的修課資格
規則。單純的向量檢索雖能處理語意相似，卻無法精確處理結構化關係與資格過濾。

### 問題二：科系探索缺乏具體感

高中生選填科系時，最常見的困境是不知道「這個科系的人實際上在做什麼研究」。招生簡章寫的
多半是抽象的系所簡介；而國科會大專生研究計畫是由真實大學生完成的第一手具體研究題目，內容
卻是寫給學術審查看的正式全文，對高中生來說門檻太高、讀不下去。本專案的 PDF 研究計畫系統
把這些真實計畫轉化成高中生看得懂的摘要，再進一步生成**興趣量表**——高中生不用啃完一篇論文，
只要針對每份計畫的動機、方法、成果回答幾個簡單問題，系統就依科系累加分數，推薦最符合他們
興趣的科系。**興趣量表是本專案最核心的特色**：它把「讀懂一篇研究計畫全文」這個對高中生幾乎
不可能的任務，轉換成「回答幾題有沒有興趣」，讓科系探索不需要先看懂論文。

這正是本專案想解決的問題：**如何整合 LLM、知識圖譜與多種檢索策略，建構一套能同時處理語意
模糊查詢、結構化關係查詢與資格過濾的教育領域 RAG 系統，並讓高中生也能透過真實研究計畫的
摘要與興趣量表，快速理解與定位自己對什麼樣的研究有興趣。**

## 設計理念

- **模組化 RAG，而非單一管線。** 系統不是「檢索—拼接—生成」的線性流程，而是把路由、多路
  檢索融合、迭代式檢索、自我修正、長期記憶拆成可組合的模組——依問題複雜度動態決定要用多輕
  或多重的策略，簡單問題不需要跑完整套深度研究迴圈。
- **知識圖譜是檢索索引，不是全域摘要。** 圖譜的角色是支援多跳關係查詢與 Personalized
  PageRank 概念擴散、並把圖信號融合進向量排序（graph-as-index），而不是像 Microsoft
  GraphRAG 那樣預先生成整個語料庫的階層式社群摘要——本系統要精確回答「哪些系所必修某技術」
  這類結構化問題，而非做全域主題歸納。
- **會自己承認不會，而不是硬答。** 每個 agent 完成任務後會自我評估證據是否足夠，不足就
  「逃逸」升級給更強的下一位（chat → retrieval → research），但換手次數有上限，保證不會
  無限循環；證據不足時明確標示，而非產生看似合理實則捏造的答案。
- **設計對象是高中生，不只是大學生。** 修課資格、研究計畫全文對高中生來說門檻太高，因此
  興趣量表用 AI 把真實研究計畫改寫成高中生看得懂的導讀與題目，讓「探索科系興趣」這件事
  不需要先看懂論文。

## 核心功能

前端共 8 個頁面，但背後只有兩套 AI 系統在服務：選課相關的問題都交給「課程智能助理」的 ReAct
Agent，直接查 Hybrid 檢索與知識圖譜作答；研究計畫相關的問題交給「PDF 研究計畫多代理人」，先
由 Orchestrator 判斷難度——簡單問題 chat agent 幾秒答完，複雜問題才升級到 research agent 跑
完整的 coverage-driven 檢索迴圈。兩套系統最後都收斂到同一個 FastAPI 服務，共用 Azure OpenAI、
Qdrant、Neon PostgreSQL 三項核心雲端服務。

| 頁面（導覽列） | 路由 | 你可以做什麼 |
|------|------|------|
| **課程助理** | `/course-search` | 用自然語言問選課問題（找課、查修課資格、比較課程、跨技術探索），AI 邊查邊答 |
| **課程資訊** | `/courses` | 依學院／系所瀏覽全校課程，關鍵字或語意搜尋，最多同時比較 3 門課 |
| **系所修課** | `/curriculum` | 查詢各系所畢業規定、必修/選修學分結構，樹狀瀏覽課程規劃 |
| **研究計畫** | `/projects` | 瀏覽歷年國科會大專生研究計畫，開啟 PDF 原文並直接用 AI 問答 |
| **興趣量表** | `/assessment` | 針對研究計畫摘要作答，依高一／高二／高三提供不同分組與科系推薦 |
| **資源連結** | `/resources` | 落點分析、甄選入學等升學資源，以及各學院系所官網目錄 |
| **個人分析**（登入後） | `/profile` | 從自己的對話歷史看探索型態、興趣領域雷達圖 |
| **系統監控**（開發者專用） | `/monitor` | 用量、費用、延遲即時儀表板 |

### 這些頁面實際能幫高中生回答什麼問題

**興趣量表：看出你適合什麼樣的研究，而不是只看科系名字。** 高中生選填志願常常只看到「機械
工程學系」這種名字，不知道實際內容是什麼。興趣量表不問「你喜歡機械系嗎」，而是先把真實研究
計畫轉成幾個具體情境問題，讓你在不知道背後是哪個科系的情況下，憑直覺選你有興趣的研究動機、
方法與成果——回答完幾份計畫的題目後，系統依你勾選的科系累加分數，才顯示「你最符合機械工程
學系、光電科學與工程學系」這類推薦，而不是先入為主地照科系刻板印象猜。

**課程助理：看出科系之間真正的差異，也看出科系跟你想的不一樣。**
- 「機械系跟土木系有什麼不一樣？」→ 用高中生看得懂的方式比較兩系的核心課程與能力培養方向，
  不是直接丟兩份課綱給你比對。
- 「資工系是不是每天都在寫程式？」→ 可以列出資工系實際的必修/選修分布，也能順便查「哪些系
  所同樣有教 Python」——例如地球科學系、財務金融學系的課程裡也有資料分析/程式相關選修課，
  破除「只有資工系才需要寫程式」的印象。
- 「我對中文系有興趣，但也想學一點寫程式，可以嗎？」→ 全校開放的通識課與跨系學分學程（如
  「人工智慧技術應用學分學程」）本來就設計給非資訊背景學生修，課程助理可以直接查出哪些通識
  課／學程對外系開放，不用轉系或雙主修也能碰程式。
- 「這門課到底在教什麼？」→ 把課綱裡的專業術語轉譯成白話說明，而不是原封不動丟出課綱原文。

**PDF 研究計畫：看見大學生實際做出什麼成果、用什麼工具、解決什麼問題。** 國科會大專生研究
計畫是最貼近「這個科系的人到底在做什麼」的第一手資料，系統把 459 份真實計畫變成可以問答的
資料庫，橫跨 38 個系所。舉幾個資料庫裡真實存在的例子，而不只是資工系：
- **機械工程學系**的學生用高溫高壓風洞、高速攝影機與光學紋影系統量測燃燒速率；
- **地球科學學系**的學生分析深海鑽探岩心，用 X 光繞射儀（XRD）與螢光光譜儀（XRF）研究造山
  運動如何影響全球氣候變遷；
- **光電科學與工程學系**的學生用高解析度光纖光譜儀量測糾纏光子對，做的是量子計算的基礎研究；
- **天文研究所**的學生分析歐洲太空總署羅賽塔號拍攝的彗星影像，重建 67P 彗星的地質結構；
- **中國文學系**的學生用文本分析法系統性整理《詩經》裡的水意象。

高中生可以直接問「機械系的研究計畫都在用什麼設備？」「地球科學系可以解決什麼問題？」，AI
會從真正的研究計畫全文裡找答案，並用導讀與興趣量表把它轉成看得懂的語言——不用先弄懂論文，
就能感受到「這個系的人真的在做這件事」。

## 技術亮點

### 1. 知識建構管線：課程不只是課名，圖譜不只是 NLP 萃取

![知識建構管線](png/圖1-知識建構管線.png)

每一門課進到系統後，不是只有課名跟課號兩個欄位。四個分工的 LLM Agent（本地 Qwen3-14B 推理，
不用付 API 費用）從課綱與教師資料萃取語意標籤，加上結構化解析出的修課規則，一門課實際上會
展開成超過 40 個 Qdrant 欄位，大致分四類：

| 欄位分類 | 代表欄位 | 來源 | 用途 |
|---|---|---|---|
| 基本資料 | `name_zh`/`name_en`/`dept`/`college`/`credits`/`teacher` | 課務系統原始資料 | 展示與基本過濾 |
| 語意標籤 | `languages`/`tools`/`concepts`（如「PyTorch」「梯度下降」） | Agent 1 萃取 | 技術/概念比對，`search_courses(tech=...)` 用 |
| 領域/主題標籤 | `domain_tags`/`topic_tags` | Agent 2（研究領域）／Agent 3（通識主題） | 依領域或通識主題精確過濾 |
| 修課資格 | `eligible_years`/`dept_include`/`prereq_codes`/`conflict_codes` | 修課資格規則解析（不靠 LLM） | 判斷「誰能修這門課」 |
| 開放對象 | `open_to_minor`/`open_to_double_major`/`is_grad_only`/`is_unrestricted` 等布林欄位 | 同上 | 「資工系大二以上、開放輔系生」這類精確過濾 |

這些欄位大多數是**用來過濾、而不是用來搜的**——這也是課程助理能做到「資工系大二以上、開放
輔系生」這種精確查詢，而不只是語意相近的原因。

知識圖譜也不是只有 NLP 萃取出來的語意節點，分兩階段建置：

1. **Phase 1（機構結構骨架，不靠 LLM）**：從課程 JSON、應修科目表、學分學程解析出
   University → College → Department → Course / GraduationRule / CreditProgram。
2. **Phase 2（語意節點補入）**：把 Agent 1～4 萃取的 Concept / Technology / Field /
   Competency 節點與加權邊補進去，並用 Jaro-Winkler 相似度（≥0.70）在同義概念間連
   `SIMILAR_TO` 邊。

目前圖譜規模 27,447 節點・103,111 邊，19 種節點類型、33 種邊類型（見「系統架構」一節的
資料層）。

### 2. 課程助理的 14 個工具：RRF 只是其中一個

![多信號 RRF 檢索](png/圖2-多信號RRF檢索.png)

課程助理不是只會做語意搜尋——ReAct 迴圈暴露了完整的 14 個工具，`search_courses` 的多信號
RRF 只是其中最複雜的一個，實際會依問題型態呼叫不同工具：

| 使用者問題 | 呼叫的工具 | 為什麼是這個工具 |
|---|---|---|
| 「資工系有教 PyTorch 的必修課？」 | `search_courses(tech="PyTorch", dept="資訊工程學系", course_type="必修")` | 技術/系所/修課別是精確過濾條件，語意相似度反而會混入不相關課程 |
| 「資工系的必修課有哪些？」 | `get_dept_courses("資訊工程學系")` | 系所必修/選修清單是結構化圖查詢，比語意搜尋更完整精確 |
| 「機器學習這門課的先修規定跟課綱？」 | `get_course_detail(...)` | 一次工具呼叫拿到課綱＋修課資格＋先修（整合工具，省一輪 LLM 往返） |
| 「資工系是在學些什麼的？」 | `get_dept_info("資訊工程學系")` | 系所介紹＋領域分布，不是可以被語意檢索的單篇短文 |
| 「資工系的畢業學分怎麼算？」 | `get_graduation_requirements("資訊工程學系")` | 畢業規定是結構化 JSON + 圖查詢，不是自然語言 |
| 「人工智慧技術應用學分學程要修哪些課？」 | `get_program_info("人工智慧技術應用學分學程")` | 學程說明＋課程清單一次拿到（整合工具） |
| 「有沒有學程可以學到資料科學？」 | `search_programs("資料科學")` | 獨立語意搜尋 `ncu_credit_programs` collection，不會被課程結果稀釋 |
| 「跟機器學習概念相近的課還有哪些？」 | `find_similar_courses("機器學習")` | 靠圖上 `COVERS` 邊算「共享概念數」，比純文字相似度更精確 |
| 「機器學習這門課教了哪些具體概念，還有哪些課也教到？」 | `get_course_knowledge_map("機器學習")` | 攤開單一課程的概念地圖，而不是找相似課程列表 |
| 「哪些系所有教 Python？」 | `get_depts_by_tech("Python")` | 「技術→系所」的圖多跳查詢，向量搜尋回傳的是課程而非系所 |
| 「和 AI 相關的系所、課程、老師有哪些？」 | `ppr_explore(seed="AI", focus="overview")` | 廣泛圖探索靠 Personalized PageRank 擴散，不是找最相似的幾筆 |
| 「哪些課涵蓋卷積神經網路？」 | `explore_concept_neighborhood("卷積神經網路", hops=2)` | 概念節點的 N 跳 BFS 鄰域，抓向量搜尋可能漏掉的間接關聯課程 |
| 「陳教授的專長跟開的課？」 | `get_teacher_info("陳教授")` | 教師專長＋開課紀錄一次拿到 |
| 「有沒有老師是做自然語言處理研究的？」 | `search_teachers("自然語言處理")` | 獨立語意搜尋 `ncu_teachers` collection，不會被課程結果稀釋 |

只有查詢裡帶技術關鍵字且沒有其他語意成分時（如單純「PyTorch 的課」），`search_courses` 才會
走 Graph-First 捷徑直接命中 `tech::pytorch` 節點，跳過六信號 RRF 流程——這也是為什麼系統把
「精確查詢」與「語意檢索」拆成兩條路徑，而不是把所有查詢都丟進同一套向量搜尋。

### 3. Research Agent：先定義要蒐集什麼證據，什麼時候才用 HyDE

![Research Agent 架構](png/圖3-ResearchAgent架構.png)

深度研究不是「查一次生成一次」，而是先把問題拆成幾個「證據槽」（coverage slot），逐輪檢索
補齊，證據足夠才動筆。這套機制**即時運作在 PDF 問答**：使用者提問時，如果 chat／retrieval
都判斷證據不足，Orchestrator 才會升級到 research agent 跑這套迴圈；下一節「興趣量表」用的
是同一套邏輯，但那是離線跑過一次的批次工作，不是即時服務，細節見下一節。

固定的四個證據槽（其他情境會動態產生不同槽位，例如下一節提到的「特色發現」「興趣切入」）：

| 槽位 | 檢索關鍵詞（search_hints） |
|---|---|
| `research_motivation` | 研究動機、研究背景、研究目的、研究問題、重要性 |
| `research_methods` | 研究方法、研究步驟、分析方法、實驗設計、資料蒐集 |
| `research_findings` | 研究成果、主要發現、結論、小結、研究結果 |
| `research_limitations` | 研究限制、未解決問題、不足、限制、適用範圍、結論 |

每個槽位有自己的狀態機（`FILLED` / `PARTIAL` / `NOT_FILLED` / `EXHAUSTED` / `NOT_FOUND`），
reflector 每輪評估後才決定要不要繼續查、換槽位查，還是收斂寫作。

**HyDE 不是每次檢索都開。** `should_use_hyde()` 只有在（a）已經有前幾輪的檢索結果或下一步
搜尋方向，**而且**（b）這個槽位本身是解釋性/衍生性問題（槽位描述裡出現「有趣」「特色」
「亮點」「導讀」「興趣」之類字眼就算），**或者**前幾輪檢索連續槽住沒有新證據／槽位狀態是
`PARTIAL`，才會生成假設性文件去檢索。實際對照：

| 使用者問題 | 對應槽位 | 開不開 HyDE？ |
|---|---|---|
| 「這篇研究用了什麼方法？」 | `research_methods`（事實性，文件章節可以直接對到） | ❌ 不開——用原問題關鍵字查「研究方法、研究步驟」就找得到 |
| 「這篇研究最特別、最吸引人的地方是什麼？」 | 動態產生的 `distinctive_findings`（衍生性，描述含「特色」） | ✅ 開——「特別、吸引人」不是論文原文會出現的字眼，要先讓 LLM 生成一段假設性描述再去檢索 |
| 「這篇研究的方法有什麼創新？」（追問，前幾輪已查過方法但答得不夠深） | `research_methods`，狀態變成 `PARTIAL` | ✅ 開——不是因為衍生性，而是弱檢索補救 |

也就是說 HyDE 是「查不到才加開的第二招」，不是預設策略，避免每次都多花一次 LLM 呼叫生成
假設文件。cross-slot 路由則是讓某次檢索找到的證據，如果同時也能回答另一個槽位，會直接標記
另一槽位為部分完成，不用重複查詢。

### 4. 興趣量表與摘要欄位怎麼來的：一次性離線 ETL，不是即時服務

`/assessment` 頁面的興趣量表題目，還有 `/projects` 頁面每份計畫顯示的
`motivation`/`method`/`result`/`tags` 摘要欄位，**都不是使用者打開頁面時才叫 AI 現場生成
的**。這點值得說清楚，因為很容易被誤以為是即時功能：

```
使用者上傳/瀏覽 PDF
      │
      ▼
Parsing + Chunking + Indexing（供即時聊天檢索用）
      │
      ▼
── 沒有任何批次摘要／題目生成呼叫 ──
```

正式站台收到 PDF 後只做向量索引，不會自動觸發摘要或量表生成。這些欄位的真正來源是：在另一
個開發分支上，對 459 份 PDF 全部跑過一次完整的 Research Agent 管線，把結果匯出成快照，再用
一支匯入腳本把資料寫死合併進 `data/processed/projects.json` 與
`data/processed/assessment_questions.json` 這兩個靜態檔案——正式站台只唯讀服務這兩個檔案。

**這次離線生成實際跑了什麼**（4 個步驟，Step 2、3 平行執行）：

| 步驟 | 做什麼 | 輸入 | 輸出 |
|---|---|---|---|
| Step 1 | Research Agent 對這份 PDF 跑上面的 coverage-driven 檢索（最多 10 次搜尋） | 固定問題：「請整理研究動機、方法、成果與限制」 | 一段高資訊量的原始研究摘要（純文字） |
| Step 2 | 用一顆 LLM 把 Step 1 的文字結構化 | Step 1 的輸出 | `{motivation, method, results, tags}`，前三欄各限 200 字，3～5 個標籤 |
| Step 3 | 另一顆 LLM 把 Step 1 的文字改寫成高中生導讀＋量表題目 | 同一份 Step 1 輸出（跟 Step 2 平行跑） | `{intro, questions}`，導讀 100～220 字，3 題各 45～80 字 |
| Step 4 | LLM 依動機/方法/成果/限制四維度加權評分，低於門檻重跑一次 Step 1 | Step 1-3 的結果 | 0～5 分品質分數，不合格觸發重試 |

**Step 3 的 3 題不是隨便問的**，prompt 明確要求三題分別對應三種視角、語氣要明顯不同：

1. **情境吸引力**——「如果你可以……」「想像你站在……」，讓學生想像自己進入這個研究場景；
2. **研究方式吸引力**——把摘要裡具體的方法/工具/資料寫進題目，讓人感受到「實際在做研究」；
3. **思考方式吸引力**——偏抽象，講這門學科怎麼理解世界，不重複前兩題的場景或方法。

prompt 裡附的實際範例之一（光學物理領域）：

> **輸入**：比較二維與三維傅氏轉換在全像光鉗中控制光場的效果差異。
>
> **輸出 intro**：光有動量——這不是比喻，是物理事實。如果你把光束塑形得夠精準，它就能把比
> 頭髮細千倍的粒子「夾」在空中懸著不動，這叫全像光鉗。這份研究要解決的問題是：計算全像片時，
> 用二維傅氏轉換還是三維傅氏轉換，哪個讓光鉗更穩定地抓住樣品？
>
> **輸出 questions**：①「想像你站在實驗室前，看見一束雷射光把一粒比細菌還小的樣品懸在空中
> ……」②「這份研究需要分別計算兩種傅氏轉換產生的全像片，再用雷射實驗觀察哪種讓光場更穩定
> ……」③「物理學家說，當你真正理解一個現象，你就能說出它為什麼『必須』是這樣……」

**還有一個有趣的轉用**：Step 3 原本的設計語意是「針對這一篇論文，判斷你對這篇研究有沒有
興趣」，但匯入題庫時，題目被打散、按系所重新分組、跨論文抽樣組成題庫（依系所輪流取題，
避免某幾系的論文擠在一起），從「單篇論文的興趣探測」變成「跨論文的科系適性測驗」——你在
興趣量表裡看到的每一題，其實原本是某一篇具體研究計畫的專屬問題。完整流程與程式碼位置見
`docs/09-architecture-diagrams/fig5-extraction-pipeline.md`。

### 5. Orchestrator 動態路由與三層記憶：誰能寫、什麼時候寫

![Orchestrator 動態路由](png/圖4-Orchestrator動態路由.png)

每個 agent（chat / retrieval / research）完成後回傳一份自我評估 `AgentStatus{completed,
work_summary, gaps, agent_limitation}`，`agent_limitation` 是型別化的逃逸理由（`NONE` /
`CONTEXT_INSUFFICIENT` / `SINGLE_POINT_LOOKUP` / `RESEARCH_BUDGET_EXHAUSTED`），不是自由
文字堆疊，方便之後統計「哪種逃逸理由最常發生」。retrieval 的自評邏輯是個具體例子：只要有
找到來源、回覆長度 ≥30 字就算 `completed`，否則標記 `SINGLE_POINT_LOOKUP` 逃逸給下一位。

chat agent 還有一個更即時的自我偵測機制：如果模型判斷「這樣答下去證據不夠」，會在回覆
**最後一行**輸出字面量 `[INSUFFICIENT_CONTEXT]`。系統逐 token 累積回覆、偵測到這個哨兵
字串後，會送出一個「清空畫面」訊號讓前端丟掉已經串流出去的內容，再無縫接上逃逸後其他 agent
的正式回答——不會留下一段「答一半被打斷」的殘留文字。

這份自評結果由 Orchestrator 判讀：不足就「逃逸」升級給下一位（chat → retrieval →
research），最多跑 3 次決策、2 次換手，保證不會無限循環。

三層記憶的讀寫權限不是三個 agent 平等共享，程式碼裡有一張明確的 `MEMORY_WRITE_POLICY` 表：

| Agent | 對話摘要（context_summary） | 長期語意記憶（semantic_memory） | 使用者畫像（user_profile） |
|---|---|---|---|
| `research` | ✅ 結構化寫入 | ✅ | ✅ |
| `retrieval` | ❌ | ❌ | ❌ |
| `chat` | ⚠️ 另有一條路徑：成功回答時寫一則輕量 Q+A（非結構化，不經過這張表） | ❌ | ❌ |

- **對話摘要**只在本輪對話內有效，是決定性（deterministic）組出來的，不呼叫 LLM。
- **長期語意記憶**用 Postgres + pgvector 儲存，寫入前會先用相似度搜尋比對，**同一份文件內
  相似度 ≥ 0.92 的問題直接跳過**，避免使用者反覆問類似問題時塞爆記憶庫；只有登入使用者（非
  匿名 session）才會寫入。
- **使用者畫像**是唯一會另外呼叫一次 mini-model（`gpt-4o-mini`，temperature=0）的寫入動作，
  把新的問答觀察併入既有畫像，一樣只限登入使用者。

這代表：只跟 chat 對話幾句，系統不會記得你是誰、對什麼有興趣；只有問題複雜到升級給 research
agent 完整跑完一輪，才會沉澱進長期記憶，下次對話才查得到。
